# WordPress Sandbox — Phase 1A

Dockerized WordPress replica of `fluidcontrols.com/products/railways/`, used as
the safe target for Phase 4's WordPress auto-apply connector. This sandbox is
**not production** and must never be exposed publicly without the nginx Basic Auth
proxy.

---

## SEO Plugin Fingerprint

**Plugin: Yoast SEO** ✅

Confirmed by querying the live site's WP-JSON API:
```
GET https://fluidcontrols.com/wp-json/
"namespaces": ["yoast/v1", ...]
```

No RankMath, All in One SEO, or SEOPress markers found in page source or API
namespace listing. The live site runs **Yoast SEO** as its SEO plugin.

### Phase 4 connector meta field names (Yoast)

| Field | WP postmeta key |
|---|---|
| SEO Title | `_yoast_wpseo_title` |
| Meta Description | `_yoast_wpseo_metadesc` |
| Canonical URL | `_yoast_wpseo_canonical` |
| noindex | `_yoast_wpseo_meta-robots-noindex` |

These fields are stored in the `wp_postmeta` table and are exposed via the Yoast
REST API namespace (`yoast/v1`). When patching via the standard WP REST API
(`wp/v2/pages/{id}`), `_yoast_wpseo_*` meta fields are included in the `meta`
object if Yoast registers them as REST-accessible (which it does in Yoast ≥ 14.x).

## Slider Revolution — Content Location

**Finding: Slider Revolution is NOT used on the /products/railways/ page.**

The live site has Slider Revolution 5.4.8 installed (visible in generator meta),
but the Railways page content is stored entirely in `post_content` as WPBakery
Page Builder shortcodes (`[vc_section]`, `[vc_row]`, `[vc_custom_heading]`, etc.).

**Implication for Phase 4:**
- Phase 4's WordPress connector can patch the Railways page via the standard
  `POST /wp-json/wp/v2/pages/{id}` REST endpoint without any special Slider
  Revolution handling.
- `post_content` field → patchable via REST API `content` property.
- Yoast meta → patchable via REST API `meta` property (with Yoast's REST support).
- **No separate serialized meta fields required for Slider Revolution on this page.**

If Slider Revolution content needs to be patched on other pages in the future,
it typically stores slide data in `post_meta` as serialized PHP, which would
require a custom WP-CLI script or plugin endpoint (not REST-patchable directly).

## Quick Start

```bash
cd sandbox/wp-docker

# Start all services (nginx, wordpress, db)
docker compose up -d

# Watch provisioning (wpcli one-shot — exits when done)
docker compose logs -f wpcli

# After provisioning completes, run verification
chmod +x verify_rest_api.sh
./verify_rest_api.sh
```

## Access

| URL | Credentials | Purpose |
|---|---|---|
| `http://localhost:8091/` | nginx: `sandbox` / `sandbox123` | Public-facing (Basic Auth protected) |
| `http://localhost:8091/wp-admin` | WP: `admin` / `Admin@Sandbox1` | WordPress admin |
| `http://localhost:8091/wp-json/wp/v2/pages?slug=railways` | nginx: `sandbox` / `sandbox123` | REST API |

> **Note:** Port 8090 (raw WordPress) is not published externally. All access
> goes through the nginx Basic Auth proxy on 8091.

## Application Password (REST API)

Generated by WP-CLI during provisioning. Read from logs:

```bash
docker compose logs wpcli | grep "Password:"
```

Use in REST API calls:
```bash
curl -u sandbox:sandbox123 \
     -H "Authorization: Basic $(echo -n 'admin:<APP_PASS>' | base64)" \
     http://localhost:8091/wp-json/wp/v2/pages/<PAGE_ID>
```

> Store the app password in your `.env` as `WP_SANDBOX_APP_PASS` for Phase 4.

## Privacy / noindex

- `blog_public = 0` (WP "Discourage search engines" setting)
- `_yoast_wpseo_meta-robots-noindex = 1` on the Railways page
- `robots.txt` contains `Disallow: /` (mounted read-only into WordPress container)
- nginx Basic Auth on port 8091 — no unauthenticated access to content

## Reset

To fully reset the sandbox (destroys all data):

```bash
docker compose down -v
docker compose up -d
```
